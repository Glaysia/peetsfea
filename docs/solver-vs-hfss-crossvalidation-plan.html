peetsfea · pfsolver(open-source CUDA full-wave) vs HFSS · 6.78 MHz

교차검증 계획: 오픈소스 CUDA 솔버 ⟷ HFSS 터미널 Z-파라미터

동일한 fixed SSW 코일 STEP(src/peetsfea/data/0.3.x_fixed.toml → ssw_scene.step)에 대해, HFSS terminal full-wave(ferrite-enabled 실측 완료, no-ferrite 완료)와 오픈소스 CUDA full-wave Python API pfsolver(solver/pfsolver 독립 서브모듈, inspect/mesh/rank1·rank2·rank4 solve 구현, numeric calibration 필요)가 6.78 MHz에서 같은 Z(f)·L·M·R·C·k를 내는지 검증한다. pfsolver rank4 결과는 §4·§5에 채웠고, 현재 numeric parity는 FAIL이다. 4-솔버 준정적 비교는 별도 문서 em-cross-validation-plan.html 참고.

1. 목적과 합격 가설

둘 다 full-wave terminal-network 솔버다. 같은 형상·같은 포트·같은 주파수면 같은 Z가 나와야 한다 — 이를 정량 확인하고, HFSS 라이선스 없이 동일 결과를 재현할 수 있음을 증명한다.

검증 대상 양 (6.78 MHz)
  • Z11, Z12, Z22 — 2-포트 임피던스(양쪽 1차 산출)
  • L1, L2, M, k — im(Z)/ω 유도
  • R1, R2, Q1, Q2 — re(Z), AC 손실
  • C1, C2 / SRF — full-wave라 self-resonance 직접 산출
  • 손실·field — copper/ferrite loss, air-gap B-plane, field plot 이미지 첨부
왜 pfsolver도 full-wave인가
  • HFSS full-wave가 무조건 가장 정확(M3D AC/Electrostatic/Q3D는 실측 탈락).
  • pfsolver = Python API orchestration + Palace wrapper + Palace Driven(변위전류 포함) → E·H·C·L·손실·SRF 전부.
  • HFSS와 정식화가 같으므로 준정적 솔버보다 tight tolerance를 기대.
  • CUDA mandatory · 4-core MPI · CPU 폴백 없음.
no-ferrite와 ferrite 경계: 1차 no-ferrite 검증은 stock Palace 0.16.1로 충분하다. ferrite 단계에서는 upstream Palace material 모델이 Permeability(실수 μ)·Permittivity·LossTan(유전체)·Conductivity만 지원하므로 — 페라이트 자기손실 μ″(= magnetic loss tangent)과 주파수 종속 μ(f)를 넣을 항이 없다. HFSS는 이걸 magnetic_loss_tangent + pwlx($mu,Freq)로 모델링한다. 따라서 ferrite 검증 때만 Palace fork로 복소 μ(자기손실) + 주파수 종속 material을 추가한다. Palace는 우리가 owns하는 내부 full-wave core이므로 이 패치는 정당한 작업이다(§6 M-fork).
합격 가설(full-wave↔full-wave): mesh 수렴 후 L1·L2·M ±5%, |Z| ±5%, k ±10%, C/SRF ±10%, R ±15%(표피 메시 민감) 이내 일치. Z12/Z21 부호는 port current 방향으로 추적해 공통 postprocess에서 고정. 불일치 1차 원인 후보: 메시 밀도(표피), 포트 정의, region 경계, ferrite μ 모델. 솔브 시간(비용)도 함께 기록 — HFSS 기준 282초(GPU·4코어·11 pass), pfsolver 목표 Mode 1 ≤30분.

3. HFSS 기준값 — ferrite-enabled(참고) + no-ferrite(1차 기준)

1차 비교는 no-ferrite다. pfsolver의 첫 solve는 stock Palace 0.16.1로 no-ferrite 단일주파수다(ferrite 복소 μ는 M-fork 후). 따라서 pfsolver를 맞댈 정답 기준선은 "HFSS no-ferrite"다 — 같은 fixed 형상에서 TX MULL ferrite만 non-model(solve 제외)로 바꿔 재실행한 값. 아래 ferrite-enabled 표(3.1)는 참고이고, no-ferrite 표(3.2)가 §4·§5의 실제 기준이다.

4. pfsolver (Palace full-wave) rank1·rank2·rank4 solve 완료

오픈소스 CUDA full-wave 경로. solver/pfsolver Python API가 같은 STEP을 gmsh로 메시 → Palace wrapper(~/.local/bin/palace)가 stock palace:0.16.1 엔진 솔브 → port S/V/I → Z(f). 기본 4-rank acceptance는 완료됐고, 1차 비교 대상은 §3.2 HFSS no-ferrite다. 현재 수치 비교는 FAIL이며, 다음 보정 대상은 Palace conductor boundary와 air-domain/absorbing-boundary 모델링이다.

현재 설정 (HFSS와 정렬)
  • 문제 유형: Driven(주파수영역 full-wave), GOAL1은 6.78 MHz point. sweep 0.1–100 MHz는 M5b.
  • 포트: LumpedPort ×2 (1_T1/2_T1), Z₀=50 Ω 기준, current 방향 명시.
  • 재질: copper σ=5.8e7, FR4 εr/tanδ upstream OK; ferrite 복소 μ(135.6 − j0.296, tanδ_m 0.00218) fork 패치 필요; vacuum/helper domain + 흡수경계 모델은 numeric 보정 대상.
  • 메시: gmsh(OpenCASCADE)로 STEP→tet, physical group으로 body/port/boundary 태깅.
  • 실행: peetsfea-facing CLI 없음. Python API가 CUDA Solver.Device=GPU + 4-core MPI Palace wrapper를 호출, HYPRE Umpire pool은 free VRAM/MPI rank 기준으로 adaptive 설정.
현재 Palace 증거: stock palace:0.16.1 로컬 이미지와 ~/.local/bin/palace wrapper가 동작한다. run/pfsolver_no_ferrite_mesh/palace_config.json dry-run 통과, pfsolver.solve_bundle(..., mpi_ranks=1) 진단 solve는 run/pfsolver_no_ferrite_solve_rank1/*를 생성했고 wall time 26.0 s를 기록했다. mpi_ranks=2 MPI 진단 solve도 run/pfsolver_no_ferrite_solve_rank2/*로 완주했고 wall time 28.5 s, Palace peak memory total 1.8 GiB를 기록했다. 기본 mpi_ranks=4 acceptance도 run/pfsolver_no_ferrite_solve_rank4/*로 완주했고 manifest는 pfsolver_commit=a5cb138, wall time 27.2 s, GPU free 5289 MiB, HYPRE pool 86.7 MB/rank, Palace peak memory total 3.1 GiB를 기록했다. postprocess unit test는 2-port S→Z, z*_ohm 컬럼, port-S↔port-V 검증, non-reciprocal Z reject를 포함해 통과한다.

추출식 (Palace 출력 → Z)

port-S.csv → S(f); Z = Z₀ (I+S)(I−S)⁻¹ (Z₀=50Ω 기준, 정규화)
port-V.csv 검증: S_ij = V_total[i,j] / V_inc[j,j] − δ_ij, port-S.csv와 일치해야 함
L = im(Z)/ω, R = re(Z), M = im(Z12)/ω, k = M/√(L1·L2), Q = ωL/R
C·SRF: sweep에서 im(Z)=0 인 f₀ → C = 1 / ((2πf₀)²·L)
부호 함정: Z는 port-S.csv에서 산출한다. Palace의 port-V/I.csv는 open-circuit Z 행렬이 아니므로 직접 V/I로 Z를 만들지 않고, V_inc+total V로 S를 재구성해 port-S.csv와 일치하는지 검증한다. HFSS와 같은 port current 방향으로 고정한 뒤에만 표를 채운다.

6. solver 구현 계획 (pfsolver)

구조 = pyaedt→ansysedt. pfsolver는 solver/pfsolver 아래의 독립 Python API 서브모듈(pyright strict + pydantic)다. peetsfea-facing CLI는 만들지 않고, peetsfea가 나중에 Python API를 import/call한다. 컨테이너 안엔 Palace 엔진만 들어가며, Python API가 Palace wrapper를 CLI(JSON/CSV) 경계로 호출한다.

M6 — 검증 사다리 확장
