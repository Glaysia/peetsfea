# peetsfea 0.2.20

Release Date: `TBD`

## 한 줄 요약
- 0.2.20은 `examples/type1.toml`의 숫자 literal baseline과 테스트를 분리하고, 예제 TOML 검증을 구조/지원범위 hard-fail 중심으로 재정리하는 릴리즈로 잡는다.

## Highlights
- `examples/type1.toml`은 더 이상 "현재 기본 상한/하한/count 문자열이 정확히 이 값이어야 한다"를 회귀로 고정하는 대상이 아니다.
- 예제 TOML 관련 테스트는 "파싱 가능", "필수 키/섹션 존재", "지원되지 않는 path/형식은 즉시 실패"를 보는 smoke/preflight 성격으로 축소한다.
- selection/constraint/determinism/geometry 테스트는 예제 TOML 전체 literal에 기대지 않고, 목적별 최소 fixture/spec builder를 사용하도록 분리한다.

## Breaking Changes / Migration
- `examples/type1.toml`의 sampled numeric range를 사용자가 조정하더라도, 그것만으로 unrelated test가 대량으로 깨지는 구조는 0.2.20 범위에서 제거한다.
- 예제 TOML drift 검사는 "shape/required keys/support policy" 중심으로 남기고, numeric baseline equality 검사는 기본 정책에서 제외한다.

## Public API / Interface Changes
- 새 공개 TOML path나 manifest field를 추가하는 작업은 아니다.
- 공개 계약 변화는 테스트 정책과 예제 spec 검증 범위 정리에 한정한다.

## 0.2.20 계획
- `examples/type1.toml`은 runnable example이지만, validation/constraint/selection 로직의 숫자 baseline fixture SSOT로 취급하지 않는다.
- example-spec 테스트는 아래만 hard fail 대상으로 본다.
  - TOML 문법 자체가 깨짐
  - sampled tuple 형식이 잘못됨
  - 필수 키/섹션이 누락됨
  - removed path / unknown path / unsupported path가 들어감
  - `spec_version` 또는 공개 지원 범위를 벗어남
- 예제 TOML의 개별 sampled range 값 자체는, 값이 지원 범위 안에 있는 한 사용자가 바꿔도 core regression의 기본 실패 원인이 되지 않게 한다.
- 목적별 테스트는 `examples/type1.toml` 전체 문자열 replace 방식에서 벗어나, 테스트 의도에 맞는 최소 TOML fixture 또는 dedicated builder를 사용한다.

## 작업 분할

### 1. Example Spec Test 역할 축소
- `examples/type1.toml` 관련 테스트를 smoke/preflight 계층으로 내린다.
- 확인 범위는 파싱 가능 여부, 필수 section/path 존재 여부, removed/unknown path 차단, sampled tuple shape validity 정도로 제한한다.
- 완료 기준: 예제 TOML test가 숫자 baseline drift 때문에 깨지지 않는다.

### 2. Core Validation Test 분리
- manifest validation / constraint / determinism / selection 테스트는 예제 TOML literal을 직접 baseline으로 잡지 않는다.
- 테스트 목적별 최소 fixture를 둬서, 한 테스트가 필요한 path만 명시적으로 제어한다.
- 완료 기준: core logic test가 `examples/type1.toml`의 sampled 상하한/count 숫자 변경과 직접 결합되지 않는다.

### 3. Fixture 정책 정리
- `tests/fixtures/type1_spec.py`가 example TOML literal mirror 역할을 하는 범위를 줄인다.
- fixture는 "테스트가 필요한 최소 공개 구조"를 재현하는 용도로만 남기고, runnable example의 모든 숫자 baseline 동기화를 목표로 두지 않는다.
- 완료 기준: fixture 변경 없이 example TOML sampled range를 조정할 수 있고, 필요한 테스트만 목적에 맞게 수정된다.

### 4. Hard-Fail 정책 명문화
- preflight/runtime이 무엇을 즉시 실패시켜야 하는지 문서와 테스트에서 분명히 나눈다.
- 예: malformed tuple, missing required key, unsupported path, incompatible spec version.
- 반대로, 지원 범위 내 sampled baseline tuning은 hard-fail 대상이 아님을 문서에 명시한다.
- 완료 기준: "형태/지원범위 오류"와 "사용자 튜닝 가능한 baseline"이 테스트 정책상 분리된다.

### 5. 검증 / 마감
- 최소 검증 범위는 example-spec smoke validation, manifest validation, selection/constraint/determinism 회귀, fixture/type-check 정리다.
- `.venv/bin/pytest`와 `.venv/bin/pyright` 기준으로 마감한다.
- 완료 기준: example TOML의 범위 숫자를 바꿔도 smoke/preflight 정책을 벗어나지 않는 한 unrelated regression이 깨지지 않는다.
