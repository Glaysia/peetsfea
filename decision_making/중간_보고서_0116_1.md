# 중간 보고서 0116-1

## 1. 프로젝트 개요
peetsfea는 TOML 명세(SSOT)를 기반으로 Pyaedt를 사용해 결정론적으로 설계를 생성하고, 대량 데이터셋을 생산하는 분산 실행 라이브러리다. 동일한 TOML + 동일 버전 + 동일 시드가 동일 결과로 이어지도록 설계되며, 원격 실행(SSH/Slurm)과 모니터링까지 포함하는 것이 목표다.

## 2. 계획된 기능 요약
- Spec/TOML
  - 표준 TOML 기반 스키마 정의, 검증, 정규화
  - (TOML + seed) => 결정론적 파라미터 확정
  - 사전 검증(preflight)에서 지원/미지원 항목 명시
- 실행/분산
  - 로컬/SSH/SSH+Slurm 실행 경로
  - 작업 매니페스트(파라미터, 시드, 버전, 타깃 정보, TOML 해시)
  - 원격 스테이징과 실행 계획(병렬 분배)
  - Fabric 기반 원격 실행
- 모니터링
  - 작업 단계별 타임아웃과 하트비트
  - 집계 상태와 테이블 기반 모니터 뷰
  - 머신 행 확장 시 프로세스 상세(상태/단계/경과시간/설계/TOML/AEDT 등)
- 백엔드
  - Pyaedt 의존부를 독립 모듈로 분리
  - 최소 실행 엔트리포인트(스펙/시드/출력 경로)
- 설정/식별
  - TOML을 읽어 runtime config(머신/프로세스 제한/Slurm 설정)로 반영
  - TOML 해시를 사람이 읽기 쉬운 고유 문자열(예: “친절한 아리스토텔레스”)로 매핑

## 3. 좋은 점
- Spec-first와 결정론 원칙이 명확해서 재현성과 추적성이 강하다.
- 실행/백엔드/모니터링을 레이어로 분리하여 교체 가능성을 확보했다.
- 고동시성(500+ 작업)을 목표로 한 상태 집계/모니터링 방향이 분명하다.
- 원격 실행을 SSH/Slurm까지 포함해 실제 운영 시나리오를 커버한다.

## 4. 개선/보완 필요
- TOML 스키마와 runtime config 매핑이 아직 미정이므로 설계 초기에 합의가 필요하다.
- “GUI 의존 없음” 원칙을 지키기 위해 모니터 UI는 선택적 의존으로 유지해야 한다.
ㄴ 이건 Ansys aedt 를 gui 끄고 쓴다고 시뮬레이션만 도는거야 그걸 의미하는거니까 관련해서 오 이해된거 수정할 문서 있으면 수정해
이 보고서는 수정하지 마 
- 해시→친화적 이름 매핑은 충돌 관리가 필요하므로 알고리즘과 단어 목록을 명확히 해야 한다.
ㄴ 형용사 200개 학자 300명 + 해시 두글자 뒤에 붙이는걸로 하자
- 모니터링 데이터 스키마(필수/옵션 필드, 업데이트 주기)를 공식화해야 한다.
- 테스트 전략(결정론/스펙/원격)을 단계적으로 구체화할 필요가 있다.

## 5. Divide and Conquer 옵션
### 옵션 A: 2개 분할
- A: Spec/결정론/설정 + 실행/원격
- B: 백엔드/모니터링/문서
장점: 팀이 작아도 관리가 단순함
단점: 책임 범위가 넓어 속도와 품질 저하 위험
ㄴ 이걸로 결정할게

### 옵션 B: 3개 분할
- A: Spec/결정론/설정
- B: 실행/원격/스케줄링
- C: 백엔드/모니터링/문서
장점: 실행/스펙의 병렬 진행 가능
단점: 모니터링과 백엔드가 묶여 우선순위 충돌 가능

### 옵션 C: 4개 분할
- A: Spec/결정론/설정 매핑
- B: 실행/원격/Fabric/Slurm
- C: 백엔드(Pyaedt) 통합
- D: 모니터링/관측성/UI/리포트
장점: 책임과 인터페이스가 명확, 병렬 개발 최적
단점: 관리 포인트 증가, 인터페이스 정의가 필수

## 6. 권장 분할안 및 이유
권장: **옵션 C(4개 분할)**
- Spec/결정론/설정 매핑이 SSOT의 핵심이며 다른 레이어의 계약을 결정한다.
- 실행/원격/Slurm은 Fabric 도입과 스케줄링 전략에 집중해야 한다.
- 백엔드(Pyaedt)는 다른 모듈과 독립적으로 테스트/교체 가능해야 한다.
- 모니터링은 데이터 계약과 UI/CLI 보고 체계를 독립적으로 발전시킬 수 있다.

## 7. 주요 의사결정(수립)
1) TOML→config 매핑을 우선 정의한다.
   - 머신 항목: name, ip_address, ssh_key_path, use_slurm, slurm_strategy, max_processes, aedt_version.
ㄴ TOML이 가지는건 설계에 대한 일대일 대응이고, 시뮬을 돌리는건 파이썬 소스코드로 사용자가 알아서 관리하는거야
2) TOML 해시는 SHA256 기반으로 고정하고, 친화적 이름은
   - 형용사+철학자/인물 리스트에서 결정
   - 충돌 시 숫자 접미사로 해소(예: calm-marx-02)
ㄴ 형용사+학자리스트+해시앞두글자 로 결정했어
3) Slurm 전략은 기본을 sbatch 제출 + 상태 조회로 정하고,
   - 고급 옵션으로 srun/attach 모드를 지원한다.
ㄴ srun으로 하자
4) 모니터 데이터 스키마를 문서화하고, 프로세스 상태 업데이트 주기를 명시한다.
