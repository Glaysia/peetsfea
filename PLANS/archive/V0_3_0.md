## PHASE5~10 드리프트 정리 원칙
- 계획 문서의 단계명과 실제 코드 객체명/테스트명이 불일치하면 실패로 간주한다.
- 중간 구현으로 생긴 임시 명칭(alias)은 V0.3.0에서 제거하고 단일 명칭으로 통합한다.
- "구현됨"의 기준을 문서가 아니라 테스트/검증 로그 기준으로 고정한다.
- 단계가 공용화되었으면 타입 문서에서 중복 서술하지 않고 공용 계약만 참조한다.

## Type1 종속 vs 공용 코드 분류 기준
Type1 종속 코드:
- 특정 형상 규칙(`tx_dd`, `tx_vertical`, `rx_dd`) 또는 Type1 endpoint 라벨 규약에 직접 의존한다.
- Type1 배치/미러/브리지 규칙 없이는 의미가 없다.

공용 코드:
- 타입과 무관한 계약(`입력 검증`, `em policy`, `결과 계약`, `validation gate`)으로 표현 가능하다.
- 타입별 입력 어댑터만 바꾸면 동일 로직을 재사용할 수 있다.

분류 의사결정 규칙:
- 질문 1: "Type1 이름을 제거해도 성립하는가?"
- 질문 2: "입력 TypedDict 계약만 맞으면 다른 타입에서 재사용 가능한가?"
- 둘 다 Yes면 공용으로 분리한다.

## 목표 구조 (계약 정의만)
- 공통 영역: `src/peetsfea/core/*`
- 타입 전용 영역: `src/peetsfea/types/type1/*`
- 외부 진입점:
  - `run`
  - `build_square_spiral_from_manifest`
- 위 진입점은 V0.3.0에서 시그니처를 즉시 변경하지 않고, 내부 매핑 계약만 정의한다.

## 네이밍 정합성 규칙
- 계획명 = 코드 모듈명 = 테스트 시나리오명이 동일 루트 토큰을 공유해야 한다.
- 금지:
  - 문서에는 `phaseX`, 코드에는 다른 도메인명 사용
  - 타입 전용 로직이 `common/core` 네임스페이스에 잔존
- 권장:
  - 계약 중심 이름(`*_contract`, `*_adapter`, `*_validation`)
  - 타입 접두사 명시(`type1_*`) 또는 타입 디렉터리로 캡슐화

## 수용 기준 (리팩토링 + 테스트 고정)
- Type1 종속과 공용 코드 경계가 문서와 동일하게 정의되어 있다.
- 공용 계약 문서가 타입 수 증가 시에도 재사용 가능한 형태로 닫혀 있다.
- 네이밍 드리프트를 허용하지 않는 규칙이 문서/테스트 체크리스트에 반영되어 있다.
- `V0_3_1~V0_3_3`는 기능 재정의 없이 버전 이관 문서로만 유지된다.
