이 브랜치(dev/3)의 목적은 오픈소스 C++ FEM 솔버를 만드는 것이다. 기존 프로젝트구상.md에서 C++ 솔버는 Phase 7, 가장 마지막에 놓여 있었다. 그 foundation surrogate 연구 자체는 다른 프로젝트들에서 점진적으로 진행 중이므로, 여기서는 그 순서를 뒤집어 C++ FEM 솔버를 최우선이자 핵심 deliverable로 끌어올린다.

솔버는 Ansys HFSS 라이선스 병목을 없애기 위해, peetsfea 0.3.7이 결정론적으로 생성하는 ssw_scene.step + 추출된 ledger/token + field 데이터를 입력으로 받아 terminal network Z(f)를 추출한다. HFSS를 100% 대체하는 것이 아니라, "현재 프로젝트가 추출하는 정보 + field 데이터" 범위 안에서 HFSS의 Z-파라미터 역할을 대체한다.

§2배경 — 왜 자체 솔버인가

WPT 코일·변압기 설계 성능은 인덕턴스, 상호인덕턴스, 결합계수, AC 저항, Q, 손실, 효율로 결정된다. 공진형 WPT의 figure of merit은 다음과 같다.

\[ U = k\sqrt{Q_1 Q_2}, \qquad Q_i = \frac{\omega L_i}{R_i} \]

따라서 \(L, M, k\)뿐 아니라 \(R, Q\), 손실 예측이 핵심이다. 현재 이 값들은 HFSS terminal Z(f) 추출에 의존하는데, 3D full-wave / quasi-static FEM은 얇은 도체, skin/proximity effect, ferrite loss, adaptive mesh, port normalization 때문에 설계 1점당 수십 분이 걸리고, 무엇보다 Ansys 라이선스가 병목이다.

핵심 문제

대규모 surrogate corpus를 만들려면 수만~수십만 점의 Z(f)를 풀어야 하는데, 상용 라이선스로는 동시성·비용·자동화가 모두 막힌다. → 라이선스 프리, GPU 가속, headless 자동화가 되는 자체 C++ FEM 솔버가 필요하다.

사전조사(Phase 0)에서 Palace(AWS Labs, C++17, MPI/CUDA 가능 오픈소스 3D FEM)가 주파수영역 driven 시뮬레이션과 lumped/wave port S·V·I·field 출력을 제공함을 확인했다. Phase 0 sanity(phase0_sanity/)에서 CUDA 빌드·GPU 기동·cylinder/CPW 예제의 port-S.csv 산출까지 검증되었다. Palace를 FEM 코어로 채택하고, 그 위에 0.3.7 STEP을 먹이는 ingestion·mesh·postprocess·Z-추출 C++ 레이어를 우리가 만든다.

§4솔버 범위와 비범위

In scope

  • 주파수영역(frequency-domain) driven 해석만. transient는 비범위.
  • terminal-network-equivalent 출력: 2-port S/Z 행렬, 포트 V/I, 파생 \(L_1,L_2,M,k,Q_1,Q_2,\eta,U\), 손실(copper/dielectric/ferrite/boundary), 선택적 field.
  • HFSS식 full-wave driven 정식화 단일 경로(변위전류 포함 → E·H·캐패시턴스·SRF·유전손실 전부). 부분물리 솔버(M3D AC/Electrostatic/Q3D)는 실측에서 탈락.
  • lumped port excitation, port current 방향·reference impedance 명시.

Out of scope (이 브랜치)

  • HFSS의 GUI·재질 라이브러리·full RF 기능 100% 재현.
  • Transformer surrogate 학습 자체(다른 프로젝트). 여기서는 label 공급과 warm-start 수용만.
  • 형상 생성 로직 변경. STEP은 0.3.7 계약을 따른다.

실패 정책 (fail-fast)

Palace 실행이 요구된 terminal-network 출력을 재현하지 못하면 부분 결과로 degrade하지 않고 backend run을 실패시킨다. silent fallback·log-and-continue 금지. raw solver 파일은 report 수식·부호·단위·mesh 설정을 감사할 수 있을 만큼 보존한다.

§5CUDA / 병렬 강제 규약

Hard requirement

  • CUDA mandatory — CUDA가 없는 환경에서는 의도적으로 실행 거부한다. no CPU fallback (느리고 관리 부담만 늘어남).
  • 빌드: palace@0.16.0 +cuda, cuda_arch는 타깃 GPU에 맞춤(검증 데스크탑 RTX 3070 → cuda_arch=86).
  • 병렬: 4-core MPI 고정 launch + GPU 디바이스 solve(Solver.Device = "GPU").
  • 기동 시 nvidia-smi로 GPU·VRAM 확인 → 없거나 부족하면 즉시 raise(가짜 성공 금지).

Phase 0에서 8 GB RTX 3070 세션은 기본 HYPRE/Umpire CUDA 할당이 과도해 cudaMalloc … out of memory로 abort했고, HYPRE pool-size override(phase0_sanity/hypre_pool_override/)를 적용해야 GPU smoke가 통과했다. 따라서 솔버 런처는 VRAM에 맞춘 pool-size 설정을 1급 파라미터로 노출하고, full sweep의 OOM을 mesh/주파수 분할로 흡수한다.

참고: 0.3.5 runner는 이미 nvidia-smi GPU 감지 → AEDT GPU 가속(고정 cores=4) 패턴을 쓴다. 자체 솔버는 같은 4-core 규약을 따르되, AEDT와 달리 CPU 폴백을 제거한다.

§7수치 정식화

full-wave 터미널-네트워크로 확정 — 부분물리 솔버는 경험적으로 탈락

실측 비교에서 Maxwell 3D AC(H field, eddy-current), Maxwell 3D Electrostatic(E field), Q3D 같은 quasi-static/부분물리 솔버는 HFSS full-wave 대비 정확도가 떨어졌다(특히 \(R,Q,\eta\)·self-resonance·용량성 거동). 결론은 HFSS식 full-wave가 무조건 가장 정확하다는 것. 따라서 이 솔버는 변위전류를 포함한 full-wave driven 정식화(Palace Driven 모드)로 HFSS terminal-network 솔루션을 그대로 재현하는 것을 유일한 기본·검증 경로로 둔다. transient는 바라지 않으므로 비범위. 결과는 lumped terminal port → S/Z 행렬(=terminal network). 이래야 E·H field 모두, 턴간/권선간 캐패시턴스, self-resonance(SRF), 유전 손실이 HFSS처럼 잡히고 \(Z=R+jX\)의 \(X\)가 유도+용량을 일반적으로 표현한다.

주파수영역 full curl-curl(완전 Maxwell):

\[ \nabla\times\!\left(\tfrac{1}{\mu}\nabla\times \mathbf{E}\right) - \omega^2\varepsilon\,\mathbf{E} + j\omega\sigma\,\mathbf{E} = -j\omega\,\mathbf{J}_s \]

\(-\omega^2\varepsilon\) 항이 변위전류 = 캐패시턴스·E field의 출처다. 이 항을 빼면 곧 eddy-current 식 \(\nabla\times(\tfrac{1}{\mu}\nabla\times\mathbf{A}) + j\omega\sigma\mathbf{A} = \mathbf{J}_s\)(= Maxwell 3D AC)이 되어 캐패시턴스가 사라지고, 반대로 \(\nabla\times\mathbf E\approx 0\)만 두면 Electrostatic(E field)·Q3D가 된다. 세 경우 모두 실측에서 full-wave보다 부정확했으므로 이 솔버는 항을 모두 유지한 full-wave만 쓴다.

도체에는 \(\sigma\), 유전체(FR4·vacuum)에는 복소 유전율 \(\varepsilon(\omega)=\varepsilon'(1-j\tan\delta)\), 페라이트에는 복소 투자율 \(\mu(\omega)=\mu'-j\mu''\)(loss)를 부여한다. 포트별 단위 여기로 풀어 admittance 열을 얻고 Z로 역변환한다.

\[ \mathbf{Z}(f) = \mathbf{Y}(f)^{-1}, \qquad Z_{ij}=\left.\frac{V_i}{I_j}\right|_{I_{k\neq j}=0} \]

등가회로 파라미터(저주파 유도 우세 구간에서 의미를 갖고, SRF 부근에서는 full \(Z(f)\) 곡선을 1차 산출물로 본다):

\[ L_i = \frac{\Im\{Z_{ii}\}}{\omega},\quad R_i=\Re\{Z_{ii}\},\quad M=\frac{\Im\{Z_{12}\}}{\omega},\quad k=\frac{M}{\sqrt{L_1 L_2}},\quad Q_i=\frac{\omega L_i}{R_i} \]

물리 일관성 제약(post-check, 위반 시 fail): 상반성 \(\mathbf{Z}=\mathbf{Z}^{\mathsf T}\), passivity \(\Re\{\mathbf{Z}\}\succeq 0\), \(R>0,\ L>0,\ |k|\le 1\).

왜 full-wave 단일 경로인가 (경험적 근거)

§10대리모델 결합 (모드 2·3)

모드 2 — warm-started FEM

대리모델은 mesh 자체를 생성하지 않는다. mesh 생성은 솔버가 하는 쉬운 단계이고, 대리모델은 mesh 밀도(refinement density) 맵과 초기 EM field만 예측한다. 솔버는 이 밀도 맵으로 mesh를 생성하고 예측 field를 초기 guess로 써서 adaptive pass 수를 줄여 ≤15분에 정밀 해로 수렴한다. 솔버는 이를 위해:

  • 외부에서 주입된 mesh 밀도 맵(target edge length / refinement field)을 수용해 mesh를 생성하는 입력 경로
  • 초기 vector potential / field를 solver 초기값으로 로드하는 hook
  • 밀도 가이드 유무와 무관하게 같은 수렴 기준·같은 출력 계약 보장(공정한 시간 측정)

모드 3 — surrogate-only

솔버는 직접 호출되지 않는다. 대신 모드 1이 생산한 high-fidelity (STEP/token → Z(f)) label로 학습된 대리모델이 0.1초에 추론한다. 이 브랜치의 책임은 label 품질·provenance 추적: HFSS label, Palace label, cross-solver-calibrated label을 구분 기록한다.

geometry token = 정규 ML 입력

스크린샷·CAD 파일명이 아니라 coil_making_token.toml의 action token(role·material·layer·conductor path·port endpoint·ferrite domain·boundary)을 대리모델의 canonical 입력으로 쓴다. 토큰 payload는 scalar/list/ref-only·결정론적이어야 하며, 같은 token 스트림이 geometry ledger·mesh intent·solver config·ML feature를 모두 재생성한다.

§12리스크

  • Port normalization: 정확한 두 솔버가 부호·정규화 때문에 틀려 보임 → 공통 postprocess에서 고정.
  • Mesh near port gap / copper edge: Rac·Q를 지배 → refine 규칙을 명시·고정.
  • Ferrite 모델 차이: HFSS와 μ/loss 모델이 다를 수 있음 → ferrite 비교 격리.
  • 6.78 MHz 대형 air domain: 파장(~44 m)≫코일이라 full-wave FEM이 저주파에서 ill-conditioning·수렴 난조를 겪을 수 있음 → 도메인/경계 크기·preconditioner 관리, 필요시 low-frequency-stabilized full-wave 사용. 부분물리 솔버는 실측에서 탈락했으므로 정확도를 버리는 도피는 없다.
  • GPU VRAM: 8 GB급에서 기본 할당 OOM → pool-size override + mesh/freq 분할. CUDA 강제이므로 CPU 회피 불가(설계상 수용).
  • ML label solver bias: HFSS/Palace 불일치 미추적 시 label 편향 → provenance 필수.

§13상위 연구 맥락 — foundation surrogate

아래는 원본 프로젝트구상.md의 비전을 보존한 요약이다. 이 브랜치의 C++ 솔버는 그 비전의 데이터 기반(data foundation)을 담당한다.

중심 명제

전자기 설계는 최종 CAD 형상이 아니라 물리 의미를 가진 실행 가능한 생성 과정이다. 이를 physical IR token으로 표현해 Transformer foundation surrogate로 사전학습하면, 새로운 설계 family에 소량(수십~수백) fine-tuning만으로 적응할 수 있다.

핵심 검증 목표:

\[ \text{Foundation surrogate} + 100\ \text{target} \;\approx\; \text{classical surrogate} + 100{,}000\ \text{target} \]
  • 입력: design IR token(coil/turn/layer/ferrite/port primitive) + 물리 수치 token + 관계 graph + solver setting.
  • 출력 head: \(\mathbf{Z}(f)\) · 등가 \(L,R,M,k\) · physics-consistency \(Q=\omega L/R\) · loss \(P_{cu},P_{fe}\) · field latent.
  • loss: \(\mathcal L_Z + \lambda_1\mathcal L_{LRM} + \lambda_2\mathcal L_Q + \lambda_3\mathcal L_\eta + \lambda_4\mathcal L_{loss} + \lambda_5\mathcal L_{phys}\) (passivity·상반성 제약 포함).
  • 검증: held-out target family에서 \(R,Q,\eta\) 중심으로 데이터 효율 \(10^2\!\sim\!10^3\)배 절감 입증.

이 surrogate 학습 자체는 다른 프로젝트들에서 진행된다. dev/3은 그 corpus와 모드 2의 warm-start 엔진, 그리고 모드 3의 정답 생성기를 만드는 오픈소스 CUDA C++ FEM 솔버에 집중한다.
