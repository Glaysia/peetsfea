# 0.3.0 Palace Second Backend Roadmap

## Summary
- Plan a Palace frequency-domain EM backend as a second solver beside HFSS.
- Keep HFSS as the reference solver until cross-solver agreement is measured.
- Establish a solver-neutral result contract before any training or dataset expansion.

## Contracts
- Backend selection is runner/build behavior and must not fork geometry semantics in TOML.
- HFSS and Palace must consume the same source design identity, geometry ledger, material ledger, port ledger, and frequency set.
- Palace output must be normalized into the same terminal-network result contract as HFSS output.
- The first Palace backend is frequency-domain only; transient support is explicitly out of scope.

## Validation
- Start with the minimal two-port baseline.
- Compare S/Z matrix, port voltage/current, units, current directions, and derived L/M/k/Q values.
- Add SSW fixtures only after the minimal comparison is understood.
- Treat ferrite and loss comparisons as separate validation stages.
